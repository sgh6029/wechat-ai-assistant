## 二、新装的 WeFlow 到底哪儿出了问题

**根因：重装把 `wcdb_api.dll` 换回了安装包里的原版，而原版这个 DLL 在这台机器上是坏的。**

安装包里自带的：

```
resources\resources\wcdb\win32\x64\wcdb_api.dll
  1,063,936 字节   2026-04-10 12:08:12   ← 安装包原版，坏的
```

它能被 `koffi.load` 成功加载，但内部自检直接失败：

```
[bootstrap] koffi.load ok
[bootstrap] InitProtection rc=-101 path=...\wcdb\win32\x64
[bootstrap] InitProtection failed finalCode=-101      ← 每秒/每40秒重试一次
```

后果是链式崩塌：

```
InitProtection 失败 → 库里一条也读不出来 → 没有新消息 → 推送流永远没有 message.new
                    → 你的助手连得上、握手 200、然后一条都收不到（就是之前那个症状）
```

**证据（`%APPDATA%\weflow\logs\wcdb.log` 时间线）**

| 时间 | 事件 |
|---|---|
| 11:00:08 | 旧安装（用我 11/24 深夜换过的 1.57MB 重编译 DLL）`getSessions ok size=132830` 正常 |
| 11:06:26 | 你重装，新进程启动 |
| 11:06:39 → 11:07:39 | `InitProtection failed finalCode=-101` × 11 次，之后**再无一条 `getSessions ok`** |
| 11:12 | 我把重编译 DLL 换回去 → `getSessions ok` 立刻恢复 |

| 11:22:48 | **真实消息推送到达**（小尚同学：测试） |

顺带说明：这个问题和你的 `messagePushFilterMode=whitelist`（132 条白名单）**没有关系**。我把推送服务的代码翻出来了（`dist-electron/main-CYwVc7t8.js` 里的 `cq` 类），它根本**没有**做白名单过滤，只做这些判断：

- 跳过 `lastMsgType === 10002` / 摘要含「撤回了一条消息」的会话
- 跳过 `isSend === 1`（**你自己发出去的消息不推**）
- 跳过 `createTime < 会话基线时间戳` 的历史消息
- 用 `messageKey` 去重（10 分钟 TTL）

所以想验证推送，必须让别人给你发消息，自己发的不算。

## 五、Bot 面板怎么用

侧边栏 **Bot** → 四个标签。

**必须理解的三个开关**（设置页）：

| 开关 | 关 | 开 |
|---|---|---|
| 自动回复 | 只记录消息，不调 AI | 收到就调 AI 生成回复 |
| 干跑 | 生成回复但**不发送** | 符合发送条件就真发 |
| 允许键盘发送 | 永远不发 | 允许用键盘自动化操作微信窗口 |

**安全公式**：`自动回复=开` + `干跑=开` → AI 会算但绝不发；两个都关掉才会真发到微信。

配置文件：`%APPDATA%\weflow\wfai\config.json`（不在安装目录，重装不丢）
本地 API：`%APPDATA%\weflow\wfai\api.json`（端口 + 令牌，只监听 127.0.0.1，供面板调用和排查用）

**WeFlow 自己的开关别忘**：设置 → HTTP API 里 `httpApiEnabled` / `messagePushEnabled` 都得是开的（现在都是开的，端口 5031）。

### 6.1 推送白名单搬进 Bot

WeFlow 的 `messagePushFilterList`（132 条）存在它自己的配置里，Bot 读不到也不会自动用。
现在 **Bot → 设置 → 联系人与范围 → 「从 WeFlow 导入推送白名单」** 一键抄过来（实测导入 132 条）。

⚠️ 两个必须知道的点：

1. **WeFlow 的推送根本不看这份名单。** 我把它推送服务的代码翻出来看过（`cq` 类），它只挡三类：撤回/系统消息、`isSend===1`（自己发的）、比基线更早的历史消息。所以真正生效的是 Bot 里这份名单。
2. **那 132 条全是私聊 wxid，一个群都没有。** 如果把它同时套到「群关键词监听 / @ 触发」上，群聊功能会静默失效。所以我把规则和名单解耦了：
   - `watch.respect_filter` / `mention.respect_filter` **默认 false**（不受名单限制）
   - AI 自动回复仍然受名单限制

### 6.2 定时归档（全本地）

- 数据源：WeFlow 自己的本地 HTTP API（`/api/v1/sessions` + `/api/v1/messages`），不联网

- 有「立即归档」「打开归档目录」按钮

### 6.3 群聊被动监听（关键词）

- **单独规则**：从目录里选任意群或人，各自设「每几小时归档」「满多少条自动压缩」，可单独开关
- 每行显示待打包条数、热文件大小、已打包 zip 个数；按钮 `归档` / `压缩` / `删除`
- 调度：主任务按 `interval_minutes` 跑；**每 60 秒**再检查单独规则有没有到点
- 压缩：把 `archive/<wxid>.ndjson` 打成 `archive/packed/<wxid>-<时间戳>.zip`（内含 ndjson），热文件清空、`pending` 归零

实测：测试群热文件 1.7KB → 压缩成 0.8KB zip → 热文件变 0 字节。

游标结构从 `{id: ts}` 升级成 `{id: {ts, lastRun, pending, rotations}}`，旧的纯数字游标自动兼容。

## 八、第四版：模型自己决定调哪个工具（function calling）

### 怎么实现的

- 把所有**启用的插件** + **内置文件工具** 转成 OpenAI `tools` 规格：

## 附录：后续修复记录

### A1. 白名单勾一下就滚回顶部（12:03 修）

**原因**：勾选复选框后走的是 `act('save')`，它会把整个设置页 `innerHTML` 重绘一遍，列表容器的 `scrollTop` 自然归零。

**修法两层**：
1. 勾选改成**就地更新** —— 只改本地名单、计数和那个复选框，只有当前在「已选」视图时才重绘（因为那一行该消失）。
2. `renderBody()` 统一**记住并恢复** `.wfai-body` 和 `#wl-list` 的滚动位置。

**实测**：把列表滚到 `scrollTop=600` 再勾一个 → 之后仍是 `600`。

### A2. 微信把会话开在「独立窗口」导致回不出去（12:02 修）

**现象**：微信 4.x 有时把某个会话单开一个窗口（比如你截图里的「测试群(5)」）。原来的脚本只认主窗口，
回车后如果前台变成了那个独立窗口，脚本判定「失去焦点」直接中止 → 回复失败。

**修法**：
- 回车**前**枚举一次微信的所有顶层窗口，回车**后**再枚举一次；出现的新窗口就是刚打开的会话，直接切过去。
- 前台窗口只要**属于微信进程**就继续（主窗口/独立窗口都行），并把 `$hwnd` 改成前台那个窗口；
  只有前台**不是微信进程**（内置浏览器）才中止。
- 开头激活那一步也改成同样的规则：前台是微信的另一个窗口就改用它，避免把字打到别的窗口。

**实测**：独立窗口开着的情况下发给「测试群」→ `WFAI_SEND_OK`，消息准确落在测试群（12:02:44）。

### A3. 两次 @ 只回一次（12:04 修）

**原因**：@ 触发的冷却复用了关键词的 `watch.cooldown_seconds`（默认 120 秒），连发几条 @ 只有第一条会回。

**修法**：`mention` 独立出 `cooldown_seconds`，**默认 0（每次都回）**；规则页 @ 卡片里多了一个「冷却秒」输入框。

### A4. 监听开关与自动回复解耦（12:00 修）

重启后推送没接上，因为原来只在 `auto_reply` 为真时才启动 SSE。现在有独立的 `listen` 开关（持久化），
点「停止监听/开始监听」改的就是它；关掉自动回复不影响 @ 触发和 `/命令`。

## 附录 B：群聊多人并发 / 发言人身份 / 图片表情 / emoji（12:14）

### B1. 多人同时 @ 会互相顶掉 → 改为按发言人分桶

**原来**：缓冲区按 `sessionId` 存，同一个群里 A 和 B 同时 @，两条消息会合并进**同一条**缓冲、只触发一次回复，而且回复不知道在回谁。

**现在**：群聊的缓冲键是 `sessionId|发言人`（`group.per_sender`，默认开）。
A 和 B 各走各的管线，各拿到针对自己的回复。实测：

```
12:11:34 张三 → @【群内昵称】 你好，A 项目现在什么进度了
12:11:35 李四 → @【群内昵称】 帮我做个PPT，两页就行
12:11:39 → @张三 你好，A 项目进度我这边没查到，你说是哪个项目…
12:11:40 🔧 plugin_pptx({"input":"汇报\n# 背景…"})
12:11:41 → @李四 做好了，PPT《汇报》已生成（标题页+背景+结论）…
```

**顺带修了一个必须修的东西**：往微信打字是键盘自动化，两条回复同时跑会互相踩。现在所有发送串行进一个队列
（`enqueueSend`），永远不会出现两个 `send.ps1` 同时在打字。

### B2. 合并消息给云端 API 带不带发言人名字

**原来不带**，合并成 `"你好\n帮我做个PPT"`，模型根本不知道谁说的。

**现在群聊一定带**，格式是 `发言人：内容`：
```
张三：@【群内昵称】 你好，A 项目现在什么进度了
李四：@【群内昵称】 帮我做个PPT，两页就行
```
并且群聊的系统提示词会自动追加一条群规则（要求逐个回应、短、不点名就用 @）。回复发出去时还会自动补 `@发言人`（`group.reply_mention`，默认开）。

### B3. 群聊回复设置独立出来

规则页新增「群聊专属（覆盖全局）」卡片：

| 项 | 默认 | 说明 |
|---|---|---|
| 被 @ 时响应 | 开 | `group.at_enabled` |
| 关键词也触发 | 关 | `group.keyword_enabled`，关掉就只有 @ 才理 |
| 回复群里的普通消息 | 关 | `group.auto_reply`，开了会刷屏 |
| 按发言人分开合并 | 开 | `group.per_sender` |
| 回复时 @对方 | 开 | `group.reply_mention` |
| 群聊合并延迟（秒） | 10 | 覆盖全局 `buffer_seconds` |
| 每分钟上限 | 6 | 同一个群别刷太快 |
| 群聊专属关键词 | 空 | 在全局关键词之外追加 |
| 群聊专属提示词 | 空 | 留空用全局 |

### B4. 图片 / 表情包

规则页新增「图片 / 表情包」卡片：

- **开关**：关掉就完全忽略图片类消息
- **三种处理**：
  - `告诉模型「某人发了图」`（默认）—— 转成「张三发了一张图片」交给模型，它能接话但看不到图内容
  - `直接回一句固定话` —— 可自定义回执文本
  - `当没看见`
- 识别的类型：图片 / 表情 / 动画表情 / 视频 / 语音 / 位置 / 名片 / 小程序 / 链接 / 文件 / 红包 / 转账 / 通话 / 拍一拍

**并且**：同一个人在 @ 你之后紧接着发的图片/表情，会**并进他那条待合并的缓冲**里，模型看到的是
`王五：@【群内昵称】 看看这张图…` + `王五：[王五发了一张图片]`。实测回复：「图我这边看不了，你把排班表文字发我」。

### B5. 禁止回复带 emoji

两层：

1. 提示词里要求不输出 emoji；
2. **发出去之前做字符级过滤**（`sanitizeReply`），覆盖 `1F000-1FAFF`（表情/符号）、`2600-27BF`（杂项符号+装饰）、`2B00-2BFF`、变体选择符、ZWJ、肤色、旗帜、keycap。

实测：把提示词改成「必须用 3 个 emoji 回复」，模型确实吐了 emoji，最后发出去的文本里
**emoji 数量 = 0**，句子本身的标点和换行都正常。

群聊回复字数上限也独立了（默认 160，私聊仍用全局 `max_reply_chars`）。

## 附录 C：被 @ 后「持续激活」（12:20）

### 是什么

在群里被 @ 一次，并不代表对话就结束了——后面大家接着聊，Bot 不该立刻失聪。所以加了**持续激活窗口**：

- 被 @ 时开启一个窗口，窗口内这个群收到的消息（**谁发的都算**）都照常走「合并缓冲 → 推送 → 回复」
- 窗口由**条数**或**时长**结束，可自己设
- 缓冲规则完全不变：仍然按群聊合并延迟（默认 10s）把窗口内的消息合并后再回

### 配置（规则页 → 群聊专属 → 被 @ 后持续激活）

| 项 | 默认 | 说明 |
|---|---|---|
| 启用 | 开 | |
| 上限条数 | **20** | 窗口内最多再处理 20 条消息 |
| 时长分钟 | **5** | 窗口最长 5 分钟 |
| 结束条件 | 按条数 | `按条数` / `按时长` / `先到先结束` |
| 激活中再 @ 会刷新 | 开 | 又被 @ 就把额度和时间重置 |
| 每条也推 Webhook | 关 | 打开后窗口内每条消息都 POST 一个 `type:"active"` 事件（带上下文） |

### 实测

**A. 持续激活扩大对话范围**（额度 20 条）

```

12:19:34 李四 → 我周六下午有空                        ← 没 @ 也算
12:19:35 王五 → 我周日全天都行                        ← 没 @ 也算
12:19:39 → @张三 这个得大家自己报名，我统计不了谁有空。@所有人 周末有空的回个1…
12:19:39 → @李四 好嘞，那周六下午定？在哪儿碰头你说
12:19:40 → @王五 好，那就周日，具体几点我看看其他人再定。
```
三条回复分别点名，互不串味。窗口状态：`剩18条 已用2`。

**B. 额度用完自然收回**（额度设 2 条）

```
12:20:11 赵六  → @【群内昵称】 在吗          ← 触发激活（额度 2）
12:20:12 群友1 → 闲聊第 1 条         ← 额度 1，回了
12:20:12 群友2 → 闲聊第 2 条         ← 额度 0，回了
12:20:13 群友3 → 闲聊第 3 条         ← 状态 filtered，不再回
```
额度一用完，立刻退回「只认 @ / 关键词」的常态，不会无限接话。

### 两个细节

1. 激活期间**同一个人**的消息仍然按发言人分桶合并，所以「A 连发三条」会合并成一条回复，「A 和 B 各说一句」会各回一条。
2. 激活窗口还能和**关键词**、**图片**共存：窗口内某人发图片，按媒体规则处理（默认转成「某某发了一张图片」交给模型）。

## 附录 D：抢不到前台 / 双窗口选错 / 拍一拍不触发（12:26）

### D1. 根因不是「找不到窗口」，是 Windows 不让抢前台

失败日志：

```
WFAI_SEND_FAILED: 微信窗口无法激活到前台（前台是 pid=24224）
```

pid 24224 是 **Microsoft Edge**（我正在跟你对话的那个网页）。Windows 有个前台锁：后台进程调用
`SetForegroundWindow` 会被静默忽略。之前的发送能成功，只是因为恰好微信在前台。

现在 `send.ps1` 里加了 `ForceForeground`，四种办法依次试：

1. `SetForegroundWindow` 直接来
2. **按一下 ALT 键**（`keybd_event`）解锁前台限制，再 `SetForegroundWindow` —— 最常用有效
3. `SwitchToThisWindow`（老 API，常能绕过去）
4. `AttachThreadInput` 附着到当前前台线程，再设

四种都失败才报错，并且报错会说清「当前前台是谁」。

### D2. 双窗口：按**窗口标题**选目标

微信 4.x 的独立会话窗口，标题就是会话名（群聊是 `群名(人数)`，比如 `测试群(5)`），主窗口标题是 `微信`。

所以搜索回车之后按优先级选：

1. **标题里包含联系人名**的微信窗口（这就是那个会话的独立窗口，最稳）
2. 回车瞬间**新出现**的微信窗口
3. 当前**前台**的微信窗口
4. 都不是 → 中止不发

选中之后再用 `ForceForeground` 抢到前台，并**再确认一次**前台确实是它；万一被别的微信窗口抢走，就用那个
微信窗口（宁可换个微信窗口，也绝不把字打到别的程序里）。

日志里会打印清楚：

```
WFAI_INFO: 目标窗口[标题匹配] hwnd=xxxx title='测试群(5)'（共 3 个微信窗口）
WFAI_INFO: 已激活微信主窗口 hwnd=xxxx
WFAI_SEND_OK contact=测试群 len=14 hwnd=xxxx
```

### D3. 拍一拍不触发：它既不是 @ 也不是普通文本

查库发现拍一拍长这样：

```

content   = "小尚同学" 拍了拍 "【群内昵称】" [烟花]
```

里面**没有 `@【群内昵称】`**，所以 @ 检测认不出来；也不是以 `[` 开头的媒体消息，所以媒体分类也跳过；
群聊默认「只认 @」，于是被判成普通消息直接丢弃。

修法：新增 `detectPoke()`，专门识别 `X 拍了拍 "Y"` 这种格式，Y 命中我任意群昵称（或就是「我」）就算被叫到。
命中后走和 @ **完全相同**的路径：触发事件（类型 `poke`）→ 开持续激活窗口 → 合并缓冲 → AI 回复。

实测（真实发送，不是干跑）：

```

12:25:42 【持续激活】测试群 20 条
```

规则页 @ 触发的卡片里多了个开关：**「拍一拍也算叫到」/「拍一拍不理」**（`mention.poke_enabled`，默认开）。

### D4. 顺手把「现在几点」这种问题本地化

之前它回答「我这边看不到时间呢，你查下手机就知道啦」——因为它根本不知道现在几点。

两层修：

1. 每次回复都在提示词后面拼一段**环境信息**：当前时间（年月日 + 星期 + 时分）、这是哪个群/私聊、
   我在这个群被叫什么、以及能力边界（能读文件、能生成文档、**看不到图片内容**）。
2. 纯问时间/日期的问题**直接本地回答**，不花一次大模型调用，也不会被模型胡诌。

实测：

```

```

## 附录 E：真的"看见"图片 + 本地表情包 + 发不出去的根因（12:48）

### E1. 「回复显示已回复，实际没发出去」的真正原因

两个坑叠在一起：

**坑一：抢不到前台。** Windows 前台锁让后台进程的 `SetForegroundWindow` 被静默忽略。
修法：`EnsureFg` 四连（直接设 → ALT 解锁 → `SwitchToThisWindow` → `AttachThreadInput`），并且在
搜索前、回车后、粘贴前各确认一次。

**坑二（决定性）：窗口抢到了，但输入框没焦点。** 微信独立会话窗口被激活后，光标不一定在输入栏里，
于是 `Ctrl+V` 粘到了消息列表上 —— 脚本以为发成功了，实际什么都没发。

修法：粘贴前**先用鼠标点一下输入框**（按窗口尺寸算：水平 60%、垂直 85.5%），再把光标放进去。
日志会打印 `已点击输入框 (x,y)`。

**顺带**：如果这个会话已经有独立窗口，直接复用，**根本不再搜索** —— 因为每搜一次微信就多开一个窗口，
这就是你说的「不小心打开多窗口」的来源。

实测（真发，独立窗口 + 主窗口并存）：


### E2. 真的把图片喂给视觉模型

WeFlow 推送里只有 `[图片]` 文本，但它的本地接口能把图**解密导出成真实文件**：

```
GET /api/v1/messages?talker=<会话>&limit=10&media=1
→ messages[].mediaLocalPath = ...\cache\api-media\<会话>\images\<md5>.jpg
```

所以链路是：收到 `[图片]` → 调这个接口取 `mediaLocalPath` → 读成 base64 → 以
`image_url` 发给模型（`data:image/jpeg;base64,...`）。

三个必须处理的细节：

1. **微信是懒解密**：第一把常常还拿不到 `mediaLocalPath`。所以取图**重试 3 次、每次隔 1.5 秒**。
2. **大图要缩**：真实照片有 8MB，直接 base64 会把请求撑爆。超过 `vision.max_kb`（默认 1024KB）就用
   `tools/resize-image.ps1`（System.Drawing）缩到长边 1280 的 JPEG，通常只剩几十 KB。
3. **模型得能吃图**：实测你的 `deepseek-flash` 就能看图。

实测：

```
我：@【群内昵称】 那张大雄宝殿的图，帮我写一句配文  + [图片]
Bot：@小尚同学 这张不是大雄宝殿啊，是Windows系统信息界面，你是不是发错了？
```

——它不但看到了图，还发现我给的描述和图不符。

**处理方式现在有四个选项**（规则页 → 图片 / 表情包 → 怎么处理）：

| 选项 | 行为 |
|---|---|
| 把真图喂给视觉模型（默认） | 上面这条链路 |
| 只告诉模型「某人发了图」 | 不发图，只给一句文字提示 |
| 固定回一句 | 自己填内容，任何图片都回这句 |
| 当没看见 | 直接忽略 |

视觉模型可以单独配（Base URL / Key / 模型），留空就用主 AI。旁边有「测试视觉（拿最近一张图）」按钮。

### E3. 本地表情包库

- 目录：`%APPDATA%\weflow\wfai\stickers`（也可自定义），把 `png/jpg/gif/webp` 丢进去即可
- 每次回复发完文字后，**让模型按回复内容挑一个**（也可以改成随机）
- 静态图**当图片发**（剪贴板位图），动图**当文件发**（保留动画）

实测：

```

挑「唉，又失败了，算了」   → 无语.png
真发一条夸奖 → 文字「@小尚同学 你脑子转得快…」后自动补发 点赞.png（微信里显示为绿色「赞」图片）
```

### E4. 顺手加的两个开关

- **回复时 @ 对方**（`reply.at_person`）：不只普通回复，`/命令` 的结果也会带上 `@发言人`
- **拍一拍也算叫到**（`mention.poke_enabled`）

### E5. 「现在几点了」这类问题本地直答

`/^(现在)?几点…$/` 这类纯时间问题不再走大模型，直接本地回「现在是 2026年11月25日 星期三 12:48」，

## 附录 I：关了「@ 对方」还在 @ —— 三个原因叠在一起（13:26）

你把两个开关都关了，它还是照 @ 不误。查下来是**三个独立原因**：

### I1. 群聊提示词写死了"要点名"（主因）

`flushBuffer` 里给群聊拼的规则是**无条件**的：

模型很听话 —— 它看到的提示词让它点名，它当然点名。这个开关从来没影响到提示词。

现在改成跟着开关走：

- 开关开：`- 需要点名时，可以用「@某人」开头。`
- 开关关：`- 不要 @ 任何人，也不要写"@某某"，直接说话。`

### I2. 两条回复路径的开关不一致

- 普通回复（`flushBuffer`）：检查 `reply.at_person` **和** `group.reply_mention`
- 命令/插件回复（`replyWithResult`）：**只**检查 `reply.at_person`

所以只关 `group.reply_mention` 时，`/命令` 的结果照样带 @。

现在统一成一个 `atPersonEnabled()`：**两个都开才 @**，两条路径共用。

### I3. 开关连点两下会失效（这个最坑）

开关的点击处理是这么写的：

```js
const draft = readRules();          // 读的是上一次轮询的 uiState.cfg
let cur = ...;  setPath(draft, path, !cur);
```

`readRules()` 读的是**旧快照**，不是你屏幕上看到的状态。所以：

- 你以为它现在是「关」，实际 `uiState.cfg` 里还是「开」
- 你再点一下，算出来又是「开」，**永远关不掉**
- 更糟的是：面板和我这边的脚本同时保存时，会互相盖掉

现在改成以**画面上那个开关的 class**为准（`swEl.classList.contains('on')`），
并在保存后立刻把 `uiState.cfg` 同步成新值。实测连点三次：

```
起始 at_person=True
第1次 → False
第2次 → True
第3次 → False
```

### 另外：模型自己硬加的 @ 也会被削掉

就算开关关了、提示词也改了，模型偶尔还是会自己写「@某某 」。所以发出去之前多一道
`stripAtPrefix()`：开头连续的 `@某某` 全部削掉（最多 6 个），日志会记
`开关关闭，已去掉模型自带的 @…`。

### 实测

开关全关（`at_person=False`、`reply_mention=False`），真发：

```
@【群内昵称】 说句晚安        → 「这才下午一点多就晚安啦？行吧，那先提前祝你睡个好觉。」
@【群内昵称】 明天几点集合    → 「这个我也不知道，群里没人说过集合时间，你问问组织的人吧。」

@【群内昵称】 再确认一次…     → 「在群里说的，不是自言自语。刚答应人家不艾特，就真没艾特。」
```

开关全开时回复仍然正常带 `@小尚同学`，可逆。

## 附录 J：不再回自己发的消息（13:36）

### J1. 为什么会出现"自己回自己"

WeFlow 的推送服务里其实有 `isSend === 1` 的过滤：

```js
if (!r || a.isSend === 1 || ...) continue;
```

但有三条缝隙让它漏过来：

1. **不是所有场景 `isSend` 都是数字 1**（某些设备/同步来源会写成别的值），严格相等就漏了
2. **表情包、图片也是消息**，一样会被推过来；Bot 刚补发的表情包转头被当成"对方发的表情"，于是它去回自己的表情包
3. **本账号在别处发的话**同样会进库、进推送

### J2. 三保险

**第一道：按发言人名字挡**

```js
function isSelfSender(sender) {
  return selfNames().some(n => n === sender);   // 默认 = mention.aliases + self_names
}
```

推送里 `sourceName` 如果是 "【群内昵称】"（也就是你自己），直接丢弃，状态记为 `self`。
可以在规则页「图片 / 表情包」卡片顶部关掉这个行为（`filter.drop_self`）。

**第二道：按内容回声挡**

每发出一条消息/一个表情包/一个附件，都记一笔 `S.selfSent`（含时间、会话、类型）。
接下来 5 分钟（媒体 2 分钟）内如果进来一条内容完全一样的文本、或者一条图片/表情，
就认定是回声，直接吃掉。这样即使 `sourceName` 变了也能挡住。

**第三道：`replyWithResult` 也记账**

`/命令`、插件、`send_file` 发出去的东西同样记录，避免命令的回复被当成新消息。

### J3. 实测

```
模拟 【群内昵称】 发文字  → 状态 self，丢弃
模拟 【群内昵称】 发表情  → 状态 self，丢弃
模拟 【群内昵称】 发图片  → 状态 self，丢弃
小尚同学 @ 它    → 正常触发并回复
```

### J4. 顺手修掉的两个问题

**① 正文里的 `wxid_【已脱敏】:` 前缀**

微信的引用消息会把原发送人拼进正文，推过来是这样的：

```
wxid_【已脱敏】: ⏎ @【群内昵称】 这个怎么说
a15295133912a: [破涕为笑]
```

模型会把这串当成发言人，读起来也脏。现在统一清洗（`cleanIncomingText`）：
去掉开头的 `wxid_【已脱敏】:`、以及"纯字母数字 id + 冒号 + [`@（`"这种形式，再去掉多余空行。

**② 合并回复的异常被静默吞掉**

`setTimeout(() => flushBuffer(key), wait)` 里 `flushBuffer` 是 async，一旦抛异常就变成
未处理的 Promise rejection —— 消息会永远停在 `buffered`，日志里什么都看不到。

现在给它加了 `.catch()`，出错会写：

```
[error] 合并回复失败(测试群): xxx
```

## 附录 L：提示词被"自动改回默认"（13:40）

### L1. 根因：轮询重绘把没保存的输入冲掉了

面板每 2~6 秒拉一次 `/state`，拿到就 `renderBody()` **整页重绘**。
设置页的提示词是一个 `<textarea>`，重绘时按 `uiState.cfg.system_prompt` 重新生成 ——
**你刚打进去、还没点保存的字就这么没了**。

更坑的是：你以为输入框里还是自己写的，其实已经被重置成旧值，
这时候点「保存」，存回去的自然还是旧提示词。

服务端本身没问题，实测直接调 API 保存后 8 秒、1 分钟都不会变：

```
保存后: 你是「测试人格」…
8 秒后: 你是「测试人格」…   一致: True
```

**修法两层：**

1. **正在输入时不重绘**（`isEditing()`）：焦点在 input/textarea/select 上就跳过整页重绘，只更新顶栏。
2. **未保存的内容要保住**（`DIRTY` 集合）：所有输入框挂 `input/change` 监听，记下被改过的 id；
   每次重绘前快照这些字段的值，渲染完再写回去。保存成功后清空。

实测：在提示词框里打「临时输入的测试提示词-不要保存」，等 8 秒仍在，
而服务端存的还是原来的值 —— 正是想要的效果。

### L2. 群聊专属提示词：新增「忽略全局默认提示词」开关

位置：规则页 → 群聊专属 → 群聊专属提示词上方。

| 开关 | 实际发给模型的提示词 |
|---|---|
| 开（默认） | **只用**群聊专属那一段 |
| 关 | 全局提示词 + 空行 + 群聊专属那一段 |

实测（`promptPeek` 接口返回真实拼装结果）：

```
开关 ON  → "你是群里的助手，只回答群相关的问题。"
开关 OFF → "你是微信聊天助手。请用简短…不超过 50 字。\n\n你是群里的助手，只回答群相关的问题。"
群聊提示词留空 → 永远用全局那一段
```

## 附录 M：忽略别人发的表情（13:46）

### M1. 问题

微信的文字表情不是一个独立消息类型，而是**混在正文里的方括号 token**：

```
[破涕为笑]           ← 整条消息就是一个表情
你好呀[微笑]          ← 表情夹在文字里
😀😀😀                ← 真 unicode emoji
```

WeFlow 的 `getMessageDisplayContent` 对 `localType=1` 直接返回 `rawContent`，
所以这些 token 原样当成文字推给 API，模型看到的是「[破涕为笑]」这种字符串。

### M2. 设置

位置：**设置页 → 行为 → 忽略别人发的表情**

| 控件 | 说明 |
|---|---|
| 开关 | 默认开 |
| 模式 ① `只忽略"纯表情"消息`（默认） | 整条只有表情就丢弃；夹在文字里的不动 |
| 模式 ② `把表情从文字里剥掉` | 先剥掉表情，如果还剩文字就照常处理；剥完为空也丢弃 |

识别范围：`[xxx]`（1~12 字、不含括号和换行）以及 unicode 表情区
（`1F000-1FAFF`、`2600-27BF`、`2B00-2BFF`、变体选择符、ZWJ、肤色）。

**不会误伤** `[图片]` `[表情]` `[语音]` `[视频]` 这些媒体标记 —— 它们在表情过滤之前就已经
被媒体分类接走了（走「喂给视觉模型 / 告诉模型发了图 / 固定回复 / 当没看见」那套规则）。

### M3. 实测

pure 模式：

```
[破涕为笑]            → emoji（丢弃）
😀😀😀                → emoji（丢弃）
你好[微笑]今天怎么样   → 原样进入后续流程
[表情]                → 走媒体规则（不是被表情过滤拦掉的）
```

strip 模式：

```
你好[微笑]今天怎么样   → 「你好 今天怎么样」   （日志：去掉表情字符）
[破涕为笑]            → emoji（剥完为空，丢弃）
```

真实 @ 也验证过：`@【群内昵称】 你好呀[微笑]` → 正常触发，回复「你好呀，有事随时说～」。

### M4. 顺手修掉的一个坑

设置页的开关用的是 `data-sw`，而且处理函数是**三个 key 的硬编码 if**：

```js

if (key === 'dry_run') …
if (key === 'send_enabled') …
```

新加的开关点下去**什么都不会发生**。现在补了通用分支：**带点的 key**

然后跑了一轮运行时用例，找出 5 个真 bug：

### O1. SSE 每 15 秒自己中断一次（最严重）

日志里长这样：

```
连接 WeFlow 推送流 (第 5 次) ...
推送流出错: aborted
推送流已连接，等待消息
```

每 15 秒一轮，无限循环。原因是：

1. `startSse()` 开头会 `stopSse()`，`stopSse` 直接 `S.sse.destroy()`
2. 被销毁的那条**旧请求**还挂着 `req.on('error')` → 立刻回调 `aborted`
3. 那个回调又调 `scheduleReconnect()` → 15 秒后再来一轮

也就是说连接其实是好的，是**我们自己在每 15 秒把它掐了再连**。掐的那一瞬间到达的消息就丢了。

修法：加连接代际号 `S.sseGen`，每次 `stopSse` 递增；所有回调先判断 `stale()`，
自己销毁造成的错误不再触发重连。另外销毁前先 `removeAllListeners('error')`。

实测：重启后连上，监视 90 秒，**0 次 aborted**。

### O2. 断线重连会清空待合并的消息（这就是"有时发了没回复"）

```js
function stopSse() {
  ...
  for (const [k, b] of S.buffers) { if (b.timer) clearTimeout(b.timer); S.buffers.delete(k); }
}
```

`startSse()` 每次都会调 `stopSse()` —— 包括**断线重连**。也就是说网络抖一下、
或者 WeFlow 重启一次，所有还没到合并时间的消息被**静默丢弃**，永远不会回复。

修法：`stopSse(clearBuffers)`。只有用户主动点「停止监听」才清空（`stopSse(true)`），
重连一律保留（`stopSse(false)`）。

### O3. 「固定回执」在群里永远不触发

```js
if (mc.action === 'ack' && (!isGroup || g.auto_reply)) { ... }
```

群里 `g.auto_reply` 默认是 `false`，所以选「固定回一句」在群里**一次都不会回**，
图片反而交给 AI 去回一句"我看不到图"。

修法：改成「这个会话本来就在聊」才回执 ——
私聊必回；群里则要求满足任一：在名单内 / 开了 `group.auto_reply` / 这个发言人正在对话中。

实测：`media-ack` 状态出现，回复正是配置里那句「图我先收着，等下细看」。

### O4. 面板每次点规则页开关都刷一条错误

我上一轮写的是 `act('state')`，但 `act` 走的是 `POST /api {op}`，而 `state` 是 `GET /state`，
所以每次都记一条 `面板请求失败: 未知操作: state`。改成 `api('state')`。

### O5. 视觉取图的时间窗口锚点没赋值

`sinceTs` 用的是 `b.startedAt`，但 `bufferMessage` 创建缓冲对象时**根本没写 `startedAt`**，
永远走兜底值。已补上 `startedAt: Date.now()`，并把容差从 20 秒放宽到 60 秒。

### 复查过、确认没问题的

| 项 | 结论 |
|---|---|
| 发送队列 `enqueueSend` | 前一个失败不会卡死后面 |
| 合并缓冲生命周期 | 取用即删除，不会重复回复 |
| 归档定时器 | 重排前先清掉旧的，不会叠加 |
| 限流 `groupRateOk` | 按 60 秒滑窗裁剪，不会无限增长 |
| 统计字段 | `stats` 的 6 个字段都有自增点 |
| 去重 / 自回声 / 表情过滤 | 六种场景实测全部符合预期 |
| 视觉多图 / 表情包挑选 / 联网 | 实测正常 |
| 真实发送 + 补表情包 | 实测 `已发送` + `已补发表情包：微信表情2.jpg` |

唯一留着的噪声是启动时那几条 `推送连接失败: ECONNREFUSED` ——
hook 比 WeFlow 的 HTTP 服务先起来，1~3 秒后自动连上，属于正常竞态，不影响功能。

### R2. 但上下文压缩原来没有

之前只有 `max_history: 6` —— 到上限**直接丢掉最早的对话**，不留摘要。也就是说：
聊到第 7 轮，第 1 轮说的"周五交付"就彻底没了，模型再也想不起来。

现在做了真正的滚动压缩。

### R3. 怎么实现的

**① 预算可设**：200K / 500K / 1M 三档，也能自己填（8000 ~ 4,000,000）。

**② token 估算**（不调接口、纯本地算）：

```js
中文 1.5 字 ≈ 1 token，英文 4 字符 ≈ 1 token
```

**③ 到阈值就压缩**：`compress_at` 默认 75%。触发时：

1. 取**最近 20 条之外**的所有旧对话（`keep_recent`）
2. 连同"上一次的摘要"一起丢给模型，要求压成一段 ≤700 字的中文摘要，
   明确要求**保留人名、身份关系、事实数据、已做的决定、还没做完的事**
3. 摘要存 `%APPDATA%\weflow\wfai\context\<会话>.json`，**重启也在**
4. 之后的每次请求，摘要作为「前情提要」拼在系统提示后面
5. 被压掉的原文**写进这个会话自己的归档 ndjson**（`type:"context-compress"`）

**④ 每轮回复结束后自动检查**，不需要手动点。

## 附录 S：定时消息（内置调度器，不靠插件）（16:35）

### S1. 为什么内置比插件好

定时功能如果做成插件，会缺三样东西，而这三样恰恰最容易出问题：

1. **持久化** —— 插件进程重启就忘了"今天已经发过没有"，会重复发
2. **错过补发** —— 电脑睡了、WeFlow 关了，醒来要能补一次；插件自己判断不了该补不该补
3. **发送队列** —— 定时发送和普通回复同时抢微信键盘会互相踩，必须共用同一个 `enqueueSend`

所以直接做进主进程，和回复管线共用同一套发送函数、干跑开关、日志。

### S2. 规则能力

一条规则能单独设置：

| 项 | 说明 |
|---|---|
| 名称 / 启用 | 每条独立开关 |
| 发给谁 | 填群名或备注（走和普通回复一样的窗口激活逻辑） |
| 类型 | **每天** / **每周**（可选周一~周日多选）/ **每月**（几号）/ **一次性**（精确到分钟）/ **每隔 N 分钟** |
| 模式 | **固定文本** 或 **AI 生成**（给提示词，到点让模型现写一条） |
| 补发窗口 | 错过多少分钟内还补发（0 = 不补） |
| 最多发 N 次 | 0 = 不限，发够自动停 |
| 群里先 @ 对方 | 单独开关 |
| 只干跑 | 单条规则就能只记录不真发 |
| 随机抖动 | 0~600 秒随机延迟，避免每天分秒不差像机器人 |

规则数量不限，每条互不影响。

### S3. 实现要点

- **每 30 秒 tick 一次**，对每条规则算"最近一次应该触发的时间点"（`prevSlot`）
- 如果这个时间点**还没处理过**（`lastRunAt < slot`）且落在容差窗口内 → 触发
- 容差 = `max(补发窗口, 90 秒)`，所以正常 tick 不会误判成"错过"
- 触发时**先把 `lastRunAt` 占位**再把任务丢进发送队列，避免同一分钟重复触发
- 启动后 4 秒先跑一次 tick，这就是**开机补发**的实现
- 每条规则记 `runs`、`lastRunAt`，界面显示"下次触发时间"

### S4. 实测

**每天型**（设 16:34，现在 16:33:02）：

```
下次触发: 16:34:00
已运行: 1 次
16:34:02 每天测试 → 测试群 | sched-dry | 每天的固定问候（干跑验证）
```

**每隔型**（每 1 分钟）：130 秒内触发 2 次，间隔约 60~86 秒（30 秒 tick 的正常粒度）。

**一次性**（一分钟后）与**手动「测试」按钮**都验证通过。

期间修掉两个 bug：

1. `interval` 类型第一次被判定为"错过"而不是触发（容差算错）
2. `startSchedule()` 重复调用会叠加多个调度器（出现了 22 秒内触发两次），
   现在会把旧的 interval 和启动补偿定时器都清掉

### S5. 我的建议

- **不要设太快**：微信对高频消息有风控，每隔 N 分钟建议 ≥ 5 分钟
- **补发窗口设 60~180 分钟**：电脑睡眠一晚醒来还能补上"早安"
- **做重要提醒时**，把 `最多发 1 次` + `一次性` 配上，避免重复轰炸
- 如果只是想让自己别忘事，还可以顺手开「群里先 @ 对方」，消息会直接弹到那人脸上
- 想验证某条规则会不会发、发什么：点规则上的**「测试」**按钮，它会立刻按规则跑一次（不等待时间点）

### S6. 界面

规则页 → **定时消息** 卡片：

- 顶部总开关 + 「+ 新增规则」+「保存规则」
- 每条规则一个块，可以直接在页面上改所有字段，右侧显示「下次 11-26 08:30 · 已发 3 次」
- 底部「最近发送」列出最近 12 次的实际发送记录（时间 / 规则名 / 收件人 / 状态 / 内容）

保存后立即生效，不用重启。

## 附录 U：重启后设置全变回默认（16:55）

### U1. 真凶不是"没存"，是"存的时候被覆盖了"

先做了对照实验：直接用 API 写一批有辨识度的值 → 重启 → **全部保留**。
所以读盘没问题，问题出在**保存这一步**。

顺着"存盘"往下查，抓到了两个具体的数据丢失：

**① 点「保存设置」会把白名单清掉**

`collectSettings()` 里这一行：

```js
list: v('#cfg-filter-list').split('\n')...
```

`v()` 在元素不存在时返回 `''`。设置页一保存，白名单就从 **132 条变成 2 条**
（实测：`磁盘 filter.list 条数 = 2`），而且还会通过 `sync_weflow` 把 WeFlow 那份也一起冲掉。

**② 表情包「一律按文件发」会退回「按图片发」**

```js
send_as: q('#st-as') || 'auto',
```

`#st-as` 不在当前 DOM 里时返回 `''`，`|| 'auto'` 就把它重置成默认值。
`pick`、`action`、`mode`、`search_url` 全是同一个写法 —— 一保存就被打回默认。

**③ 更深一层：保存用的是"内存里的旧快照"**

```js
S.cfg = deepMerge(S.cfg, patch);       // 基于内存
fs.writeFileSync(cfgFile, ...);        // 直接覆盖整个文件
```

只要有两个写入者（旧实例、定时任务里的 `saveConfig({})`、面板的另一次保存），
后写的那个就会用自己那份**旧内存**把别人的改动整片抹掉。表现就是"关了程序又变回默认"。

### U2. 三层修法

**第一层：写盘改成"读最新 + 原子替换 + 留备份"**

```js
function saveConfig(patch) {
  let disk = null;
  try { disk = JSON.parse(fs.readFileSync(PATHS.cfgFile, 'utf8')); } catch (_) {}
  const base = disk ? deepMerge(defaultConfig(), disk) : S.cfg;   // 以磁盘为准
  S.cfg = deepMerge(base, patch);
  fs.writeFileSync(tmp, JSON.stringify(S.cfg, null, 2));
  fs.renameSync(tmp, PATHS.cfgFile);            // 原子替换，不会写半截
  fs.copyFileSync(PATHS.cfgFile, PATHS.cfgFile + '.bak');
}
```

**第二层：读盘失败自动回退备份**

主文件如果被写坏，`loadConfig` 会去读 `config.json.bak` 并恢复，日志打
`已从 config.json.bak 恢复配置`。绝不再"静默用默认值顶掉用户的设置"。

**第三层：界面保存时，"元素不存在"就保留原值**

```js
const pickVal = (id, fallback) => {
  const el = els.page.querySelector('#' + id);
  return el ? el.value : fallback;      // 不在 DOM 里就退回上一次的值
};
```

白名单单独处理：**只有名单编辑框真的渲染出来时**才覆盖 `filter.list`，否则原样保留。

### U3. 实测

```
重启后  sticker.send_as=file   pick=vision   thinking=on/high   ctx=500000   白名单=132
```

另外单独验证了两个曾出问题的动作：

- 切到设置页再点保存 → `filter.list` 仍是原来的，没被清 ✓

查这个 bug 的过程中，我用 `save` 接口写测试数据，把**你的白名单从 132 条覆盖成了 2 条**，

## 附录 V：7 个界面/功能问题的修复（18:25）

### V1. 定时消息里的开关点不动

`[data-rsw]` 的统一处理会把开关路径塞进 `readRules()` 的结果里再整包保存。
但 `sched.rule.0` 这类路径不在 `readRules` 的收集范围内，于是：

1. `setPath(draft, 'sched.rule.0', true)` 生成了一个假的 `schedule.rule` 对象
2. `act('save')` 之后 `renderBody()` 又把开关画回原样 —— 看起来就是"点了没反应"

**修法**：带 `sched.` 前缀的开关只切换视觉状态、不保存，
真正落地由「保存规则」按钮统一收集（`readScheduleRules` 读的就是 class 状态）。

实测：点一下 → 视觉切换 → 点保存 → 磁盘 `enabled=False` → 重绘后开关保持关闭 ✓

### V2. 联系人归档选择器不能搜索

原来是一个几百项的下拉。现在在它前面加了搜索框 `#ar-search`，
输入时**只重建 option 列表**（不重绘整页，避免打断输入），
支持按名字或 wxid 过滤，命中项保留原选中值。

### V3. 「被 @ 后持续激活」数字和"分钟"不在同一行

原来是 `上限 [20] 条 或 [5] 分钟`，标签是独立的 `span`，窄屏会折行。
改成 `flex-wrap:nowrap` + 固定输入宽度 + 标签 `white-space:nowrap`。

实测每行子元素的 y 坐标全部一致、行高 32px，确认在一行内：

```

```

### V4. 群聊专属：全局 / 按群单独

新增「生效方式」下拉：

- **全局统一**（默认）——所有群用同一套
- **按群单独设置**——下面出现每个群的独立配置块，**没配的群自动沿用全局**

每个群能单独覆盖：被 @ 是否响应、关键词是否触发、是否回普通消息、回复是否 @ 对方、
合并延迟、每分钟上限、该群专用提示词。增删都在页面上完成。

后端由 `groupCfgFor(sessionId)` 做合并：全局为底，命中该会话的规则逐字段覆盖，
`system_prompt` 为空则不覆盖。

```

```

### V5. WeFlow 地址 / token / 微信进程 自动识别

设置页 WeFlow 卡片加了「自动识别」按钮，读取 `%APPDATA%\weflow\WeFlow-config.json`
里的 `httpApiHost/httpApiPort/httpApiToken`，并用 `tasklist` 探测微信进程名。

实测输出：

```json
{"base_url":"http://127.0.0.1:5031","access_token":"","wechat_exe":"Weixin.exe",
 "notes":["读取 WeFlow-config.json：端口 5031，token 是加密的（safe:…），沿用当前已配置的 token",
          "检测到微信进程：Weixin.exe"]}
```

⚠️ **token 在 WeFlow 里是加密存储的**（`safe:...`），只有它自己进程内能解出明文，
所以自动识别**不会覆盖**已配置的 token，只填地址和进程名，并在旁边写清原因。

### V6. 「联系人与范围」搜索框打不了中文

那个输入框每 220ms 会 `renderBody()` 重绘一次。**中文输入法正在组合拼音时，重绘会打断组合**，
表现就是拼音打进去、汉字上不了屏。

**修法**：监听 `compositionstart` / `compositionend`，
组合期间（`composing` 或 `e.isComposing`）**不重绘**，组合结束再用新值渲染并恢复光标。

### V7. 顺带

- 群聊配置里 `system_prompt` 为空时不覆盖全局，避免"每个群都被清空提示词"
- 自动识别按钮的提示文字在重绘后会丢，改成重绘后重新查询元素再写

### AB2. 处理方式：运行时劫持 IPC，不动 asar

```js
function killTelemetry() {
  const blocked = new Map();
  blocked.set('cloud:init',      { success: true, disabled: true });
  blocked.set('cloud:recordPage',{ success: true, disabled: true });
  blocked.set('analytics:getOverallStatistics', { success: true, disabled: true, data: null });
  ...（共 25 个通道）

  ipcMain.handle = function (channel, fn) {
    if (blocked.has(channel)) return origHandle(channel, async () => blocked.get(channel));
    return origHandle(channel, fn);
  };
  setTimeout(swap, 6000);   // 等 app 注册完再统一替换
}
```

### AC4. 顺手做的便携能力

**① 配置可以在程序目录里（可选）**

`hook.js` 启动时先看 `resources\wfai\config.json` 是否存在：

- 有 → 便携模式，配置/日志/归档都放在程序目录
- 没有 → 跟正常安装一样用 `%APPDATA%`

包里带的是 `config.example.json`（不会自动生效），
想整个文件夹带走就把名字改掉再填内容。

**② Bot 自动从 WeFlow 取地址和 Token**

新机器上 Bot 的 `weflow.access_token` 是空的，连不上 WeFlow 的 HTTP API。
现在面板初始化 5 秒后自动调 `window.electronAPI.config.get()`
把**解密后的明文 token 和端口**取过来写进自己的配置。

实测（故意清空 token 再重启）：

```
原始 token 长度: 32
清空后: 0
重启 40 秒后: 32，连接=True，和原来完全一致
```

### AC5. 实测：解压 → 双击 → 能用

```
解压 → WeFlow\ 和 使用说明.txt
WeFlow.exe 存在: True
Bot 文件存在: True

双击启动 → ✓ 进程运行中
         → ✓ Bot 已加载（全新配置）：监听=True 干跑=True
```

（全新配置下 `token=0` 是因为 WeFlow 还在引导页，UI 注入要等进主界面；
正常进入主界面后会自动补上，上一条 AC4② 已验证。）
